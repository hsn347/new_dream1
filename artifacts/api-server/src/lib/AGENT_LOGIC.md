## ⚙️ processTextFlow — العقل المدبر

هذه الدالة هي قلب الوكيل. تُستدعى لكل رسالة نصية بعد التجميع.

### الخطوات بالترتيب:

#### 1. التحقق من الصلاحية
```
المنطق الحالي:
- جلب المستخدم → إذا غير active → توقف
- جلب الإعدادات → إذا agentEnabled=false → توقف
- جلب إعدادات الأدمن العامة (GlobalAgentSettings)
- جلب اتصال الواتساب → إذا ناقص → توقف
```

#### 2. اكتشاف صاحب العمل
```
المنطق الحالي:
- إذا رقم المرسل = reviewWhatsappNumber → وجّه إلى handleOwnerMessage()
- صاحب العمل يستطيع: قبول/رفض طلبات، عرض ملخص الطلبات
```
> 💡 **ملاحظة**: المقارنة تتم بآخر 9 أرقام فقط عبر phonesMatch()

#### 3. إدارة المحادثة
```
المنطق الحالي:
- البحث عن محادثة نشطة (status=active) لنفس الرقم
- إذا لم توجد → إنشاء محادثة جديدة
- إذا وُجدت → تحديث lastMessage و customerName
- جلب صورة الملف الشخصي في الخلفية (لا تنتظر)
```

#### 4. فحص إيقاف الوكيل
```
المنطق الحالي:
- إذا agentPaused=true → حفظ الرسالة فقط دون رد
```

#### 5. بناء سجل المحادثة
```
المنطق الحالي:
- جلب آخر N رسائل (convWindow، افتراضي 6)
- تقليم كل رسالة لـ 350 حرف كحد أقصى
- كشف الجلسة الجديدة: إذا الفجوة > sessionGapHours (افتراضي 6 ساعات)
  → إضافة ملاحظة "جلسة جديدة" بدل سجل المحادثة القديم
```
> ⚠️ **نقطة محتملة للتحسين**: تقليم 350 حرف قد يقطع معلومات مهمة من رسائل طويلة (عناوين، تفاصيل طلب)

#### 6. اختيار مفتاح AI
```
المنطق الحالي:
- أولوية 1: chatKeyId من إعدادات المستخدم
- أولوية 2: chatFallbackKeyIds (مفاتيح احتياطية)
- أولوية 3: أي مفتاح chat نشط في النظام (global fallback)
- آلية Multi-key failover: يحاول المفتاح الأول، إذا فشل → التالي → ...
- عند فشل مفتاح → إشعار الأدمن عبر واتساب
```

#### 7. بناء السياق
```
المنطق الحالي:
- buildAgentContext(): معلومات النشاط التجاري (اسم + وصف)
  ⚠️ لا يتضمن حالياً: الحسابات البنكية، سياسة التوصيل، المناطق
  (تم بناء الكود لجلبها لكن لا يتم إدراجها في النص!)

- البحث عن الطلب النشط:
  → getActiveOrder(userId, conversationId)
  → getAnyOrderBySenderPhone(userId, senderPhone) كـ fallback
  → buildActiveOrderContext() لبناء نص الطلب

- كشف نية الكوبون:
  → messageHasCouponIntent() → buildCouponContext()

- البحث المتجهي (RAG):
  → searchChunks() يبحث عن المنتجات ذات الصلة
  → إذا وُجدت نتائج → يستبدل قسم المنتجات بالنتائج الأكثر صلة
  → إذا لم توجد → يُبقي السياق الكامل
```
> ⚠️ **خلل مكتشف**: دالة `buildAgentContext()` تجلب deliverySettings و deliveryZones و deliveryRates لكن **لا تضيفها للنص المُرجع**! الوكيل لا يعرف سياسة التوصيل.

#### 8. منطق إرسال صور المنتجات
```
المنطق الحالي:
- الاعتماد كلياً على أداة `send_product_image` لتحديد متى وإلى أي منتج يتم إرسال الصورة.
- يتلقى الـ AI قائمة المنتجات مع مؤشر (يمتلك صورة / لا توجد صورة) في `productCatalogText`.
- عندما يطلب العميل صورة، يتحقق الـ AI من توفر الصورة. إذا توفرت يستدعي الأداة، وإلا يعتذر.
- `agentBrain.ts` يعالج الاستدعاء ويربط الـ `productId` بالصورة الصحيحة.
```

#### 9. الرد بكتالوج المنتجات (تم ترقيته للذكاء الاصطناعي)
```
المنطق الحالي:
- تم إلغاء الرد الثابت (Hardcoded) للكلمات مثل "وش عندكم".
- بدلاً من ذلك، يتم دمج "قائمة المنتجات المتوفرة" (تصل إلى 30 منتجاً) في الـ System Context قبل إرسالها للـ LLM.
- يعتمد الـ LLM على هذه القائمة للرد بذكاء وتطبيق قاعدة "الخيارات المحدودة" باقتراح منتجات تناسب العميل بدلاً من سرد كل القائمة كالسابق.
```

#### 10. دمج الإعدادات (Admin Override)
```
المنطق الحالي:
- adminOverride=true → إعدادات الأدمن تفوق المستخدم
- adminOverride=false → إعدادات المستخدم تفوق (الأدمن = افتراضيات)
- الإعدادات المدمجة تشمل: اللهجة، النبرة، الأسلوب، الإقناع، الطول...
```

#### 11. استدعاء LLM
```
المنطق الحالي:
- بناء System Prompt عبر buildStrictSystemPrompt()
- تأخير اختياري (responseDelay) قبل الرد
- إرسال typing indicator
- استدعاء Groq أو Gemini حسب نوع المفتاح
- تحديد الأدوات النشطة (tools):
  → إذا orderSystem=false → لا أدوات
  → إذا returnSystem=false → استثناء request_return
```

#### 12. معالجة Tool Calls
```
المنطق الحالي (3 أدوات):

submit_order:
  - مع depositReference → حفظ الطلب ثم set_deposit_ref
  - بدون depositReference → حفظ كمسودة (save_draft)
  - حالة الطلب: pending_payment

amend_order:
  - يحدّث الطلب الموجود بالبيانات الجديدة
  - يستدعي save_draft داخلياً

request_return:
  - يبحث عن طلب approved/delivered لنفس الرقم
  - إذا وُجد → إيقاف الوكيل + إنشاء طلب استرجاع + إشعار صاحب العمل
  - إذا لم يوجد → "لم أتمكن من العثور على طلب مكتمل"
```

#### 13. استدعاء AI إضافي بعد الأدوات
```
المنطق الحالي:
- إذا نفّذ الوكيل أداة ولم يُنتج نصاً → استدعاء ثانٍ لتوليد رد
- يُحدّث سياق الطلب بعد التنفيذ
- maxTokens=600 (أقل من الاستدعاء الأول)
```

#### 14. إرسال الرد
```
المنطق الحالي:
- إذا لم يكن هناك رد → "شكراً لتواصلك معنا!"
- enqueueOutgoing() → قائمة انتظار anti-ban
  → jitter عشوائي (1.2-3.8 ثانية)
  → typing indicator بطول مناسب
  → إرسال النص ثم الصورة (إن وُجدت)
- حفظ الرد في DB
- تحديث ملف العميل (extractAndUpdateProfile)
```

## 🛡️ أنظمة الحماية

### 1. منع التكرار (Deduplication)
```
المنطق الحالي:
- isDuplicate(): نفس (userId + phone + أول 200 حرف) خلال 60 ثانية → تجاهل
- تنظيف كل 30 ثانية للرسائل الأقدم من 90 ثانية
```

### 2. حماية الفيضان (Image Flood)
```
المنطق الحالي:
- الحد: 3 صور كل 10 دقائق من نفس العميل
- بعد الحد → حفظ الرسالة دون تحليل vision
```

### 3. تجميع الرسائل (Buffer & Debounce)
```
المنطق الحالي:
- message_wait_ms: 6 ثواني (الانتظار بعد آخر رسالة)
- composing_wait_ms: 15 ثانية (الانتظار بعد إشعار كتابة)
- MAX_WAIT_MS: 120 ثانية (الحد الأقصى المطلق)
- عند وصول رسالة جديدة → إعادة ضبط مؤقت الـ 6 ثواني
- عند "composing" → إعادة ضبط مؤقت الـ 15 ثانية
```

### 4. Anti-Ban (منع حظر الواتساب)
```
المنطق الحالي:
- قائمة انتظار تسلسلية per-user (لا إرسال متوازي)
- jitter عشوائي: 1.2-3.8 ثانية بين الرسائل
- cooldown per-phone: 5 ثواني بين ردين لنفس الرقم
- حد ساعي: 180 رسالة/ساعة مع backoff 12 ثانية
```

### 5. كشف تسرب System Prompt
```
المنطق الحالي:
- cleanReplyText() يبحث عن علامات مميزة من System Prompt في رد AI
- إذا وُجدت → يُلغي الرد بالكامل
- العلامات: "تحدث باللهجة"، "قواعد التفاعل"، "استراتيجية التفاوض"...
```

## 🔧 الأدوات (Tools / Function Calling)

### submit_order
```
الغرض: حفظ طلب جديد أو تحديث طلب موجود
المعاملات المطلوبة: customerName, items, subtotal, deliveryCost, total, currency
المعاملات الاختيارية: customerPhone, customerAddress, depositReference
المنطق:
  - مع depositReference → حفظ + تحويل لـ pending_review + إشعار صاحب العمل
  - بدون → حفظ كـ pending_payment
  - التحقق من عدم وجود طلب مقفل (pending_review) لنفس الرقم
```

### amend_order
```
الغرض: تعديل طلب موجود (إضافة/حذف/تغيير منتجات)
المعاملات المطلوبة: customerName, items, subtotal, deliveryCost, total, currency
المعاملات الاختيارية: customerPhone, customerAddress, amendReason
المنطق:
  - يستدعي processOrderAction مع action=save_draft
  - يستبدل البيانات القديمة بالكاملة
```

### request_return
```
الغرض: طلب استرجاع/استبدال منتج
المعاملات: كلها اختيارية (orderId, customerName, customerPhone, reason, items)
المنطق:
  - يبحث عن طلب approved/delivered لنفس الرقم
  - يوقف الوكيل تلقائياً (agentPaused=true)
  - ينشئ سجل استرجاع في DB
  - يرسل إشعار لصاحب العمل عبر واتساب
```

## 🤖 System Prompt — هيكل الشخصية (تم تحسينه وضغطه)

يُبنى عبر `buildStrictSystemPrompt()` في `providers/groq.ts`. تم ضغطه جذرياً لتقليل التوكنز وتسريع الاستجابة:

```
1. الهوية الأساسية: "أنت وكيل مبيعات محترف... شخصية واثقة، لا تعتذر عن الأسعار".
2. الهوية المتغيرة: اللهجة، قوة اللهجة، استخدام الإيموجي، وطول الرد (من الإعدادات).
3. قواعد التفاعل الأساسية (إلزامية):
   - اكتشاف الاحتياج أولاً: يمنع منعاً باتاً سرد المنتجات عند بداية المحادثة، بل يجب سؤال العميل لاكتشاف ما يريد.
   - الخيارات المحدودة جداً (1-2 منتج فقط) بعد فهم الاحتياج (إلا إذا طلب كتالوج صراحة).
   - لا تسأل عما تعرفه (الاعتماد على الذاكرة).
   - المصدر الوحيد للمعلومات (بيانات المتجر أسفل الموجه).
   - الصور وأرقام الهواتف: لا تختلق أرقاماً. وإذا طلب العميل صورة لمنتج معين، يجب على الـ AI التحقق أولاً من قائمة المنتجات ما إذا كان المنتج يمتلك صورة، فإذا كان يمتلكها يستدعي أداة send_product_image ويخبر العميل بذلك. أما إذا لم يكن يمتلكها يعتذر بلطف.
   - لا أكواد JSON.
4. نظام الطلبات (صارم جداً):
   - جمع تدريجي (الكمية أولاً، ثم الاسم والعنوان).
   - الاعتماد (submit_order) فور اكتمال البيانات الأساسية.
   - الدفع: توفير الحسابات البنكية للمراجعة.
   - التعديل (amend_order) للطلبات المقفلة فقط بناءً على طلب العميل.
5. أسعار التفاوض (السرية).
6. تعليمات خاصة (Custom Prompt) من الأدمن.
7. السياق المدمج (Context) المُرسل من agent.ts (بيانات المتجر + الطلبات الجارية).
```

## ✅ تحديثات وحلول للمشاكل السابقة

في الإصدارات الأخيرة، تم التعامل مع المشاكل وتصحيحها كالتالي:

### 1. إصلاح سياق المتجر والتوصيل
- **الحل:** تم التعديل في `agent.ts` لجلب تفاصيل التوصيل الصحيحة (عبر `freeDeliveryAll` و `unknownLocationPolicy` و `zoneRates` الصحيحة) وإضافتها للسياق. كما تم دمج تفاصيل الحسابات البنكية (`bankAccounts`) بنجاح.

### 2. تنظيف الكود الميت ومشاكل الـ Types
- **الحل:** تم التخلص من دالة `parseOrderActions` القديمة تماماً، بالإضافة لإزالة شرط التحقق من وصل (Omqi) المعطل من قلب `agentBrain.ts`، والتأكد من مطابقة جميع الحقول مع الـ Schema بفضل الـ TypeScript Compiler (0 أخطاء).

### 3. إصلاح المتغير `effectiveSendImages`
- **الحل:** تم استبداله بـ `sendImagesEnabled` بحيث يقرأ فعلياً من الإعدادات العامة والخاصة للمستخدم بدلاً من قيمة ثابتة (hardcoded).

### 4. حل إشكالية رفض الذكاء الاصطناعي لإرسال الصور (وإرساله صور خاطئة)
- **الحل:** تم الانتقال من نظام التخمين السطحي (الذي يعتمد على الكلمات المفتاحية) إلى أداة `send_product_image`. الآن يتلقى الـ AI معلومات واضحة عن أي المنتجات تمتلك صوراً، وبناءً عليه يقوم هو بتحديد متى تستدعى الأداة لتزويد العميل بصورة دقيقة دون هلوسة.

### 5. زيادة سياق الذاكرة (`MAX_MSG_CHARS`)
- **الحل:** تم رفعه من 350 إلى 600 حرف لتجنب قطع العناوين والمنتجات المهمة من تاريخ المحادثة.

- تعريف الأداة: `providers/groq.ts → AGENT_TOOLS`

### لتعديل إعدادات الحماية:
عدّل قسم "أنظمة الحماية" ثم اطلب من AI تطبيقه على:
- `agent.ts` (dedup, flood, buffer)

### لإضافة أداة جديدة:
1. أضف التعريف في قسم "الأدوات" هنا
2. اطلب من AI إضافتها في `AGENT_TOOLS` و معالجتها في `processTextFlow()`
